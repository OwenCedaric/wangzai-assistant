## 如何核对

[文件清单](SOURCE_COMPLETENESS.json) 记录本次逐路径核对的 3,305 个文件，覆盖客户端当前实现、管理后端及本轮补入内容。补充的新测试、文档和自部署工具也在仓库中，但不冒充来自原项目的文件。

```powershell
node tools/verify-source-completeness.mjs
```

该命令扫描实际目录，检查发现的源码是否进入清单及 Git，并核对必要组件。还可通过 `--client-root=<原客户端目录> --management-root=<原管理系统目录>` 对照原项目；本次两边对照无遗漏。它不声称能证明作者电脑上所有历史文件都已公开，也不替代构建、部署或产品验收。

## 为什么仍有未上传文件

- 每个安装自己的密钥、账号密码、实际部署配置、店铺/买家数据库及业务证据快照不是源码。配置示例、生成程序和验证逻辑已公开，部署者自行生成自己的配置。
- 历史 `.baseline` 快照、旧安装包、运行实例副本不是当前实现；未将旧源码当成另一个“完整付费版”保留。当前运行源码在上述目录。
- 内部评审记录和历史截图可能包含真实业务信息，未整批上传；公开部署、验证和修复说明另行提供。
- 外部 Skill 原始包和开发代理资料不因本项目公开而自动获得再分发权。客户端当前内置规则和适配代码已保留，上游依赖通过清单下载。

未承诺提供作者的运营账号、已购买的第三方 API、短信、支付商户、模型额度或 OSS。使用者可按源码接口配置自己的服务；不需要取得作者的生产私钥才能自行部署。

## 运行与许可边界

本地启动见 [自部署说明](SELF_HOSTING.md)，管理后台见 [管理端说明](../admin/README.md)。生产 Compose 后端从仓库根目录构建 `server/Dockerfile`，管理端使用 `admin/`，但容器生产上线、完整恢复和真实平台功能仍需验收，不把源码齐全当作发布通过。

许可证仍按项目持有人的要求允许本地内部经营使用、限制未经授权的对外商业化。这是源码可见许可，不是 OSI 定义的开源许可；源码是否公开与能否商用是两回事。第三方组件沿用各自许可证。
